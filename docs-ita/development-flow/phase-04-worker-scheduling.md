# Fase 4 — Worker e scheduling

> Stato: 🚧 in corso — avviata 2026-06-25, versione di lavoro `0.4.x` · Prerequisiti: Fase 3 ✅ · [Indice del flusso](README.md)

## Obiettivo

L'automazione: il container worker (sostituisce lo stub di fase 0), gli slot per-scraper (1..N al giorno, indipendenti), il runner seriale con lock e timeout, la cache di scrape con la sua configurazione admin, i record di run e i log osservabili dall'admin.

## Risultato apprezzabile

Imposti "Dragon Store alle 14:30" e alle 14:30 lo scrape parte da solo; nella pagina admin vedi la riga di log, la run con i contatori e il battito del worker. Spegni il worker per un'ora a cavallo dello slot: al riavvio recupera.

Il feed **admin-only** `GET /api/admin/errors` (errori/warning per l'admin, `{source,type,title,description}`) include lo schema-drift come **una voce**, **solo a flag attivo** (mai sulla sonda pubblica `/api/health`, mai a utenti comuni/anonimi: è un'informazione che riguarda l'admin). Il flag `WEA_SCHEMA_DRIFT_ALERT` ha **default OFF nel codice**, ma è presente e `true` in `.env`/`.env.example` (`=false` per spegnerlo). Copre **sia le tabelle core (`Base.metadata`) sia quelle dei plugin**: il drift può stare anche su una tabella di plugin (con `MetaData` propria), quindi serve una convenzione (**DECISA 2026-06-25**): ogni `BasePlugin` espone un attributo **`table_metadata: MetaData | None`** (la `_Base.metadata` del plugin; `None` per i plugin senza tabelle, es. i notifier), raccolto dal registry in `LoadedPlugin`; il check itera `Base.metadata` + le `table_metadata` dei plugin caricati. **Obbligatorio, enforced al load**: un plugin che possiede tabelle `plugin_<id>_*` ma **non** espone `table_metadata` è **rifiutato dal registry** (`PluginLoadError`) — un plugin reale rotto non parte affatto, invece di sfuggire in silenzio al drift; `table_metadata` diventa la **fonte unica** dello schema del plugin (guida il drift-check e, in prospettiva, il `create_all`). Aggiunge una **nuova regola** nelle developer-rules vicino a CTX-R6/DB-R. Il meccanismo esatto di rilevamento dell'omissione (create_all core-driven dalla `table_metadata` vs check post-`initialize` sui nomi `plugin_<id>_*`) si fissa nell'analisi di dettaglio di 4.B0. Non sostituisce le migrazioni (Alembic non c'è ancora): in dev, per applicare un cambio di schema, resta il reset del volume. **Casi reali che l'hanno motivata (fase 3)**: (1) colonne `brand`/`tags` aggiunte alla tabella core `products` → `GET /api/catalog` 500; (2) colonna `name` aggiunta alla tabella **di plugin** `plugin_dragon_store_watches` → `GET /watches` 500 (proprio questo conferma che il check NON può limitarsi alle tabelle core). *Verifica: aggiungo una colonna a un modello (core o plugin) senza ricreare il DB → warning nei log + flag attivo, da admin) `GET /api/admin/errors` contiene la voce schema-drift; flag `false` o utente non-admin/anonimo → vuoto/403/401.*

## Definition of Done

- [ ] Scraping quotidiano completamente automatico, **un solo scraper alla volta**, con scrape-now che convive (stessi lock).
- [ ] Scenari di resilienza provati: worker giù sullo slot (recupera), run oltre timeout (terminata e marcata, la coda riparte), errore su un utente (run `partial`).
- [ ] La cache lavora: stessa query tra due utenti o due run entro l'emivita → una sola visita al sito (visibile dai contatori `http_requests`/`cache_hits`); l'emivita si governa dalla UI admin.
- [ ] L'admin risponde a "quando ha girato? com'è andata? quanto ha fatto?" senza guardare il DB.
- [ ] [docs](../../docs/) aggiornata in inglese con la sola parte implementata in questa fase (DOC-12).
